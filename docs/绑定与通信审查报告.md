### 1.2 可接受的 UI 依赖 — 线程调度

以下 ViewModel 使用 `Application.Current?.Dispatcher` 进行线程调度（从后台线程回到 UI 线程），这是 WPF 中的常见做法，但在严格 MVVM 中仍属于 Service Locator 反模式：

| ViewModel | 模式 | 说明 |
|-----------|------|------|
| **MainViewModel** | `dispatcher.InvokeAsync()` | 仅用于 `_clockTimer` 和 `OnSnapshotReceived` |
| **DashboardViewModel** | `Application.Current?.Dispatcher?.InvokeAsync()` | 首次加载 + 快照刷新 |
| **MonitorViewModel** | `RunOnUiThread(Action)` 辅助方法 | 快照应用 + 日志追加 |
| **NotificationCenterViewModel** | `dispatcher.Invoke()` | 集合变更 + 通知接收 |
| **LogCenterViewModel** | `dispatcher.Invoke()` | 集合变更 + 通知接收 |

**建议**：通过 `IDispatcherService` 接口抽象，依赖注入 `IDispatcherService.InvokeAsync()`，而非直接调用 `Application.Current.Dispatcher`。

### 1.3 正确的 code-behind — View 层的 UI 逻辑

代码-behind 中直接操作 UI 控件是合理且必要的：

| 文件 | 用途 | 说明 |
|------|------|------|
| `DashboardView.xaml.cs` | 环形进度条可视化 | WPF `DoubleCollection` 无法通过绑定更新，code-behind 监听 `PropertyChanged` 更新 UI ✅ |
| `MotorReportWindow.xaml.cs` | 打印 MotorReportWindow | 报表打印属于 View 层职责 ✅ |

这些文件中的 `using System.Windows.Controls` 引用是在正确位置（View 层），**不视为违规**。

## 2. 跨模块通信模式分析

### 2.1 当前通信架构图

```
PlcPollingService (后台轮询)
    │
    ├── SnapshotReceived (C# event) ──┬── MainViewModel.OnSnapshotReceived
    │                                 ├── DashboardViewModel.OnSnapshotReceived
    │                                 ├── MonitorViewModel.OnSnapshotReceived
    │                                 └── BackendRuntime.OnSnapshotReceivedForNotification
    │
    ├── LogReceived (C# event) ──┬── MonitorViewModel.OnLogReceived
    │                            └── BackendRuntime.OnLogReceivedForNotification
    │
    └── EventChannelService (System.Threading.Channels)
            │
            ├── _snapshotChannel (Unbounded, SingleReader) → (未消费)
            └── _writeChannel (Bounded 500, DropOldest) → BatchWriteService (批量写入DB)
```

### 2.2 C# 事件模式评估

**好处**：
- 订阅/取消订阅模式正确（所有 ViewModel 的 `Dispose` 中都有 `-=` 操作）
- `PlcPollingService` 作为单一发布者，逻辑清晰

**问题**：
1. **🔴 发布者生命周期风险**：`PlcPollingService` 是 `BackendRuntime` 的成员，而 ViewModel 通过 `BackendRuntime` 获取引用。如果 `BackendRuntime` 先于 ViewModel 释放（`Dispose` 顺序问题），事件订阅者持有的是悬挂引用。

2. **🟡 没有弱事件模式**：C# 的 `event` 模式强引用订阅者，如果 ViewModel 未正确 `Dispose`，会导致内存泄漏（虽然当前所有 ViewModel 实现了 `IDisposable` 并取消订阅）。

3. **🟡 过度依赖强引用回调**：例如 `MainViewModel` 直接调用 `MonitorVM.NoLoadStations` 的 `Concat`（MainViewModel 第 91-98 行）来构建 `HeaderStations`，这是跨 ViewModel 的强耦合。

4. **🟢 直接事件已足够**：对于这种规模的 WPF 项目（6 个工位，5-6 个 ViewModel），C# 原生事件比 EventAggregator 更简单直接，没有引入不必要的框架复杂度。

### 2.3 EventChannelService 评估

`System.Threading.Channels` 的使用是一个**亮点**：

| 方面 | 评价 | 说明 |
|------|------|------|
| **生产者-消费者解耦** | ✅ 优秀 | PollingService 不直接依赖 BatchWriteService |
| **背压控制** | ✅ 正确 | `_writeChannel` 使用 `Bounded(500) + DropOldest` |
| **批量写入** | ✅ 优秀 | `BatchWriteService` 使用 100ms 窗口 + 50 条上限批量 Upsert |
| **`_snapshotChannel` 未消费** | ⚠️ 冗余 | `_snapshotChannel` 的 `Writer.TryWrite` 写入但没有任何消费者读取，浪费了一个通道 |

**建议**：移除 `_snapshotChannel`，除非有明确的消费者。或者让 ViewModel 通过 `ChannelReader<StationSnapshot>` 消费快照，而不是订阅 `SnapshotReceived` 事件。

### 2.4 强耦合回调的具体实例

#### 实例 A：MainViewModel → MonitorViewModel（强耦合）

```csharp
// MainViewModel.cs:91-98
var allStations = MonitorVM.NoLoadStations
    .Concat(MonitorVM.NoiseStations)
    .Concat(MonitorVM.LoadStations)
    .OrderBy(s => s.Id);
```

MainViewModel 直接读取 MonitorViewModel 的三组 `ObservableCollection`，意味着：
- 无法在不修改 MainViewModel 的情况下改变 MonitorViewModel 的数据结构
- 如果 MonitorViewModel 的集合名变更，编译时即可发现，但类变更耦合高

**改进建议**：在 MonitorViewModel 上暴露一个 `IEnumerable<StationState> AllStations` 属性。

#### 实例 B：ViewModel 通过 BackendRuntime 获取全部依赖

```csharp
// 所有 ViewModel 的无参构造
this(BackendRuntime.GetSharedAsync().GetAwaiter().GetResult())
```

这是 Service Locator 模式：
- 每个 ViewModel **隐式依赖** `BackendRuntime` 的全部公开成员
- 单元测试时无法 mock 部分依赖
- `GetAwaiter().GetResult()` 存在死锁风险（当前在 UI 线程调用）

### 2.5 与 Prism EventAggregator 的对比

| 特性 | 当前方案 (C# event + Channel) | Prism EventAggregator |
|------|------|------|
| 发布/订阅解耦 | 🟡 需要持有发布者引用 | ✅ 通过 Token 类型解耦 |
| 弱引用 | ❌ 强引用 | ✅ 弱引用（可用） |
| 线程调度 | ❌ 手动 Dispatcher.Invoke | ✅ UI 线程自动推送 |
| 过滤/筛选 | ❌ 订阅所有事件 | ✅ 可通过 Filter 过滤 |
| 接口依赖 | ❌ 依赖具体事件 | ✅ 依赖 IPubSubEvent |
| 项目规模匹配 | ✅ 够用 | 🟡 过重 |

**结论**：对于 6 个工位、9 个 ViewModel 的项目规模，C# 原生事件模式**够用**，但建议引入 `IEventAggregator` 风格的轻量封装，以消除 ViewModel 对 `PlcPollingService` / `BackendRuntime` 的直接依赖。

## 3. 依赖注入生命周期审查

### 3.1 当前 DI 配置（手动 Service Locator）

```csharp
// BackendRuntime.cs — 手写工厂方法 CreateDefaultAsync()
var dbContext = new SqlSugarDbContext();                    // 单例
var repository = new SqlMotorTestRepository(dbContext);     // 单例
var userService = new SqlSugarUserService(dbContext);       // 单例
var authService = new AuthService(userService);             // 单例
var notificationService = new SqlSugarNotificationService(dbContext); // 单例
var hikvisionService = new HikvisionSdkService();           // 单例
var eventChannel = new EventChannelService();               // 单例
new PlcClientFactory(useSimulation: false)                  // 单例 (Transient 更合理)
```

### 3.2 生命周期逐项评估

| 服务 | 当前 | 推荐 | 理由 |
|------|------|------|------|
| **SqlSugarDbContext** | 单例 | **单例** ✅ | SqlSugar 支持单例 DbContext（非 EF Core），开发者也使用 `Queryable<T>` 方式确保无状态查询 |
| **SqlMotorTestRepository** | 单例 | **单例** ✅ | 无状态仓储，可以单例 |
| **AuthService** | 单例 | **单例** ✅ | 无状态，仅依赖注入的 IUserService |
| **SqlSugarUserService** | 单例 | **单例** ✅ | 操作数据且 SqlSugar 线程安全，可以单例 |
| **SqlSugarNotificationService** | 单例 | **单例** ✅ | 含 `ObservableCollection` 状态 + DB 同步，用单例保证全局一致性 |
| **PlcPollingService** | 单例 | **单例** ✅ | 内部管理 PLC 连接状态和轮询任务，必须单例 |
| **BatchWriteService** | 单例 | **单例** ✅ | 后台单个消费者，必须单例 |
| **EventChannelService** | 单例 | **单例** ✅ | Channel 实例跨消费者共享 |
| **HikvisionSdkService** | 单例 | **单例** ✅ | 海康 SDK 客户端，通常需要单例 |
| **PlcClientFactory** | 单例 | **Transient (瞬态)** 🟡 | 工厂类应为瞬态，虽然当前实现无状态不影响 |
| **所有 ViewModel** | 单例 | **单例** ✅ | MainWindow 导航架构中 ViewModel 生命周期与窗口一致，单例合理 |

### 3.3 生命周期相关风险

| 风险项 | 严重度 | 说明 |
|--------|--------|------|
| 🔴 **无正式 DI 容器** | 严重 | 手动组合 + Service Locator，无法自动管理生命周期 / 释放 / 作用域 |
| 🟡 **DbConext 单例的并发风险** | 中 | SqlSugar 文档建议为每个线程创建独立的 DbContext。如果用 `Queryable<T>` 查询可能 OK，但 `BulkUpsertAsync` 可能会并发冲突 |
| 🟡 **ViewModel 的嵌套构造** | 中 | MainViewModel 在构造函数中 new 其他 ViewModel → 无法独立测试 MainVM |
| 🟢 **App.xaml.cs 硬编码创建** | 低 | `new LoginWindow()` / `new MainWindow()` 直接写在启动代码中，无法使用 DI 注入 |

## 4. 总体评价与建议

### 4.1 评分矩阵

| 维度 | 评分 | 评价 |
|------|------|------|
| **ViewModel UI 隔离** | ⭐⭐ 2/5 | 严重违规在 HistoryVM，多处直接调用 MessageBox |
| **跨模块通信** | ⭐⭐⭐ 3/5 | C# 事件够用 + Channel 亮点，但未使用弱事件 / 事件聚合器 |
| **DI 生命周期** | ⭐⭐⭐ 3/5 | 手动单例配置基本合理，但缺少容器 |
| **整体解耦度** | ⭐⭐⭐ 2.5/5 | Service Locator 模式是主要架构债务 |

### 4.2 优先修复建议

#### P0 — 立即修复

1. **历史追溯 ViewModel → View 反向依赖**（HistoryViewModel + UserViewModel）
   - **方案**：创建 `IDialogService` 接口，将窗口创建 / 打印 / 消息框抽象为服务
   ```csharp
   public interface IDialogService
   {
       bool ShowPrintDialog();
       void ShowReport(MotorTestRecordModel motor, ISeries[] waveformData);
       Task<MessageBoxResult> ShowMessageAsync(string msg, string title, ...);
       string? ShowSaveFileDialog(string filter, string defaultName);
   }
   ```
   - 估算：1-2 天

2. **移除 DefectItem.ColorBrush（数据模型中混入 UI 类型）**
   - **方案**：数据层只保留 `Color` 字符串，改用 XAML `IValueConverter` 转换
   - 变更量：DashboardViewModel.cs 一行属性删除 + 添加 Converter 类

#### P1 — 短期优化

3. **引入轻量事件聚合器**（不需要 Prism 全量）
   - 自行实现 `IEventAggregator`（约 50 行），或使用 CommunityToolkit.Mvvm 的 `WeakReferenceMessenger`
   - ViewModel 不再直接依赖 `PlcPollingService`，改为发布/订阅 `StationSnapshotReceivedMessage`

4. **抽象 IDispatcherService**
   ```csharp
   public interface IDispatcherService
   {
       void Invoke(Action action);
       Task InvokeAsync(Action action);
   }
   ```
   - 消除 5 个 ViewModel 对 `Application.Current.Dispatcher` 的直接依赖

5. **替换 Static `BackendRuntime.GetSharedAsync()` 模式**
   - 在 `MainWindow` 构造函数中通过服务定位器获取并显式注入子 ViewModel
   - 开启单元测试路径

#### P2 — 架构演进

6. **迁移至 Microsoft.Extensions.DependencyInjection**
   - 引入 `Microsoft.Extensions.DependencyInjection` NuGet
   - `BackendRuntime.CreateDefaultAsync` 替换为 `IServiceCollection` 注册
   - 自动生命周期管理，作用域支持

7. **消除 `_snapshotChannel` 的闲置浪费**
   - 确认是否有消费者，没有则移除

8. **HistoryViewModel/NotificationCenterViewModel 的 `ExportCsv` 中 `SaveFileDialog` 调用**
   - 统一通过 `IDialogService` 处理

### 4.3 已做得好的部分

| 好的实践 | 文件 | 说明 |
|----------|------|------|
| ✅ **Channel 解耦写入管道** | `EventChannelService` + `BatchWriteService` | 生产者-消费者完全解耦，批量写入降 DB 压力 |
| ✅ **事件取消订阅** | 所有 ViewModel 的 `Dispose()` | 都在 `Dispose` 中 `-=` 事件处理程序 |
| ✅ **UI 线程安全** | 所有回调中使用 `Dispatcher.CheckAccess` | 正确防止后台线程更新 UI 集合 |
| ✅ **Interface 分离** | `IMotorTestRepository` / `IUserService` / `IAuthService` / `INotificationService` | 核心服务都有接口，便于替换和测试 |
| ✅ **ViewModelBase 设计** | 提供 `IDisposable` 基类 | 统一释放模式 |
